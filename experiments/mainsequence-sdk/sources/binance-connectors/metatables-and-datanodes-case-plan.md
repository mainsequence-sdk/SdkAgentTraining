This plan extracts case ideas from a production-style connector that combines
exchange asset metadata, account metadata, bar DataNodes, derived market-cap
DataNodes, scoped migration providers, and dynamic storage migrations.

The local checkout used for analysis was only a reading aid. Cases must cite the
public repository, package version, tag/ref, and repository-relative files in
`case_source_of_truth`.

## Important Concepts

- Exchange-specific metadata should be modeled as sidecar MetaTables linked to
  canonical platform entities, not by expanding canonical asset or account
  tables.
- Account detail tables are current metadata tables. Timestamped balances and
  positions belong in time-indexed facts, not in account sidecars.
- Bar DataNodes should use storage-first time-indexed table contracts. Supported
  frequencies must be finite and migration-owned, not created ad hoc at runtime.
- DataNode config should separate dataset identity from updater scope and
  runtime resource controls.
- Incremental updates should use per-identity update statistics and return an
  empty DataFrame for no-op runs.
- Raw exchange files can be read from primary or mirror locations, but the
  DataNode output contract still has to satisfy the SDK DataFrame validation
  rules.
- Derived DataNodes can transform identity dimensions, for example from a
  tradable pair to a base asset, but that transformation must be deterministic
  and reflected in dependency and update-window design.
- Migration providers should be explicit about model scope. Optional or dynamic
  storage tables need controlled provider construction, shared version history,
  and clear failure modes when required source metadata is missing.

## What Makes These Cases Difficult

- The same domain has durable row state, time-indexed facts, and derived
  analytics, so the correct primitive changes by task.
- Some storage classes are generated by frequency, but only a fixed supported
  set should be migrated.
- Runtime options such as memory limits, raw-file mirrors, workers, and chunk
  sizes affect execution but should not silently redefine the dataset.
- Sidecar rows must preserve one-to-one relations to canonical tables while
  adding useful lookup paths for exchange identifiers.
- Dynamic storage depends on backend metadata such as source table UID and
  cadence; missing metadata should fail clearly before execution.

## Case Families To Author

- DataNode bar publisher: fixed frequency storage, raw-file update flow,
  per-asset incrementality, and memory-safe partial progress.
- Derived market-cap DataNode: source price dependency, output identity
  transformation, static supply anchor, and incremental source windows.
- Asset sidecar MetaTable: one-to-one exchange asset metadata linked to
  canonical assets.
- Account sidecar MetaTables: spot and futures current account details linked to
  canonical accounts without storing raw secrets or balances.
- Scoped and dynamic migrations: one shared history with scoped providers for
  optional tables and a dynamic provider for source-dependent storage.
